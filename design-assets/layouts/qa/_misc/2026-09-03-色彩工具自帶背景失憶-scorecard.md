# 成績單｜2026-09-03 色彩工具・自帶背景「上傳了卻沒出現」根治（路④修東西批）

**使用者報修原話**：「已經上傳了背景圖，但是 hero module 的預覽沒有正確的呈現我上傳背景圖片的預覽，這個問題之前也反覆發生過。」
第二輪補充：「reload 瀏覽器後，重新上傳背景圖，在 hero module 的預覽一樣沒有更新背景圖」＋截圖。
動作類別＝動工具程式。**只動色彩工具一支檔案**；未碰引擎、spec、deploy-site。

**本批修掉兩個各自獨立的缺陷。第一輪只找到第二個（次要的），使用者回報「還是沒好」才挖到正主。**

---

## 缺陷 A（正主）：三支同步函式各自只看圖庫下拉，把使用者上傳的圖蓋掉

### 症狀為什麼「反覆發生」

**11 款版型裡有 8 款正常、3 款壞**。壞不壞取決於當下選中的圖庫背景是哪一類——所以看起來時好時壞、隔幾天又出現。

### 根因

`render()` 主線其實**有正確**把自帶圖設進 `--preview-hero-image`。真正出事的是旁邊三支同步函式，它們判斷「現在的背景長什麼樣」時**只讀 `$("comboBackground").value`（圖庫下拉），完全不知道使用者已經用自帶圖蓋過選擇**：

| 函式 | 做了什麼 | 後果 |
|---|---|---|
| `syncSeamlessTile()` | 選中的圖庫背景是四方連續磚 → 給外框掛 `.bg-seamless` | CSS `.page-hero-stage.bg-seamless .hero{background:transparent}` **把 hero 的底強制設成透明**＝自帶圖被蓋掉、完全看不見 |
| `syncBgPattern()` | 照圖庫背景的 `patternKey` 在 hero 上畫格紋 | 格紋蓋在使用者自己的圖上（**使用者截圖那層菱形紋就是這個**） |
| `syncBridgeExtend()` | 照圖庫背景的類別決定底部漸層 | 圖庫選中磚類時漸層被關掉，與畫面不符 |
| `comboBridgeHex()` | 回傳圖庫背景的銜接色 | 自帶圖沒有登記銜接色，卻沿用了圖庫那張的＝頁底被染成跟圖無關的顏色 |

**＝鐵律 4「同類幾處」的教科書案例**：「現在生效的背景是哪一張」這條判定散在四個消費端，當初只教會了 `render()` 一個。改了門口那道，屋裡還有三道舊的。

### 修法

立**單一判準** `customBgActive()`，四個消費端一律問它，不再各抄一份；並在註解寫明日後新增消費端也照問。

### 迴歸測試（從最外層入口打到底，專抓漏改的內門）

逐一切換**全部 11 款版型**，每款都上傳同一張自帶圖，判準＝**使用者實際看得到的那件事**：`#hero` 的 computed `background-image` 真的含有那張圖，且 `.bg-seamless`／`.bg-lattice` 都沒掛上。

| | 結果 |
|---|---|
| 修復後 | **11/11 全過**，pageerror 0 |
| **修復前（拿 HEAD 版本跑同一支）** | **3/11 失敗**＝layout-004（bg-004 磚）、layout-005（bg-028 磚）、**layout-010（bg-026 格紋＝使用者截圖那款）** |

**測試抓得到才算數**——先確認同一支測試在舊版本會紅，否則全綠證明不了任何事。

### 我自己踩的坑（記給後人）

第一輪我重現不出來，因為**我拿 layout-011 測**——那是我當天一直在做的版型，剛好是正常的 8 款之一。
教訓：**「我重現不出來」不等於「沒問題」，只等於「我挑的那組參數剛好沒踩到」。** 名單類／狀態類的 bug，一開始就該把值域全跑一遍，而不是拿手邊順手的那一個試。

## 缺陷 B（次要，同批一併修）：整支工具零持久化，重整就失憶

### 根因

工具**沒有任何一條路**能在重整後把上傳的圖接回來：

| 路 | 為什麼不通 |
|---|---|
| 記憶體暫時網址（objectURL） | 預覽唯一取圖來源，重整或跳到背景圖庫／版型庫再回來就沒了 |
| 伺服器回的網址 | `/api/pending-bg` 回 `../活動版型待審背景/<檔>`＝給部署站底下那層頁面用的相對路徑，對色彩工具指到不存在的位置 |
| 直接讀那個資料夾 | 工作台 `/活動版型待審背景/*` 路由要登入（實測 HTTP 401；只有 `/ping` 免登入） |

全檔 `localStorage`／`sessionStorage` 命中數＝**0**。

### 真正的傷害在提案包（不在預覽）

`__customBg` 一沒，打包時 `proposalPack.background` **默默退回圖庫背景**——使用者上傳的圖直接從提案包裡消失，帶進 CMS 當然沒有他的圖，**畫面上完全沒有跡象**＝鐵律 3 靜默降級，而且發生在「設計師以為自己已經交件」之後。

### 修法

- 上傳成功後把 `{id, file, name, size}` 寫進 `sessionStorage`（**只記號碼與描述、不記圖**，圖已在伺服器上）
- 重整／換頁回來自動還原號碼欄 → **提案包照樣帶號碼走**
- 便籤據實說明：「圖還在系統裡、打包會帶著走；預覽縮圖只活在上傳當下的分頁，要看畫面請重選同一個檔」——不假裝有預覽，也不無聲失去
- 修掉順帶陷阱：重選同一個檔時原本會把已領的 `pendingId` 沖掉，害提案包從「待審貨號」默默退回「只在本機預覽」
- 兩處清除路徑同步清記憶，否則重整又冒回來

### 驗收

| 查了什麼 | 結果 |
|---|---|
| `file://` 下 sessionStorage 可用嗎（修法成立前提） | ✅ true——必須實測，被擋的話整個修法是空的 |
| 重整後 | ✅ `pendingId` 還原、便籤顯示、`hasUrl:false`（誠實反映預覽沒了） |
| 重選同一個檔 | ✅ 預覽回來且 `pendingId` 保住 |
